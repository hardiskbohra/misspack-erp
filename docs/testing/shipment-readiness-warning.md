# Shipment status: packing, QC, approval and document warnings

## Decision and acceptance criteria

The updated shipment-status screenshot shows four issues: a missing confirmed Packaging List, a missing passing QC sample, incomplete Artwork and PPS approvals, and missing dispatch documents (including POD for a delivered shipment). The user explicitly wants these issues to warn rather than prevent the status update. This supersedes the earlier payment-only decision and the earlier decision to retain the pictured approval status blocker.

- Planning-to-dispatch changes from the shipment list, tracking detail, shipment edit, and status derived from history edits/deletions save despite missing or short/failed packing, a missing passing QC sample, incomplete sales-item Artwork/PPS approvals, or missing Project dispatch documents. Later status changes also warn about currently outstanding issues, including POD when becoming Delivered, without introducing new blockers. A status change must not create a receipt or document.
- The redirected office page displays the shipment number and actionable outstanding issues as escaped, accessible server-rendered text, including when JavaScript is disabled. Recheck operations-view access when displaying the details. Show a separate Proforma warning if appropriate. Do not silently treat missing evidence or approvals as complete or create an administrator override.
- Valid project-product identity and quantity remain independent controls on the first Planning-to-dispatch transition, as do permissions, hold/delay remarks, date validation and stale-status protection. Later tracking changes introduce no new blockers. Existing matching administrator overrides remain effective, and unresolved evidence is still shown as a warning. Approval workflow state and version-specific client decisions remain unchanged; this decision concerns shipment tracking only.
- Preserve the immutable dispatch evaluation, history, notifications, project readiness, financial obligations and existing gate/override audit semantics. New statuses reflect tracking, not proof of physical packing, QC, approvals, delivery receipt or paperwork. Recheck evidence under the project lock; a changed readiness-only snapshot should not itself reject the update. Planning shipment creation and edits serialize with the project quantity check; stale project or workflow bindings require a refresh. A rejected first-dispatch attempt from shipment edit or a new tracking entry records the assessed gate without partially saving the shipment or its history. A rejected history edit or deletion rolls back that history change and its attempted evaluation together. If the rejected shipment edit proposed different project or product lines, save them in Planning before asking a manager to review the current facts.
- Project workflow guidance must distinguish unresolved readiness from a tracking-status prohibition. Historical evaluation snapshots are not rewritten. Refreshing current evidence must not silently replace the project-level evaluation with a different partial shipment's evaluation, even when the represented shipment is cancelled or moved. Recheck the delivery checklist of a failed direct-delivery attempt even if POD was present at the time. A legacy, non-overridden snapshot without this context may require a fresh tracking attempt or step-level re-evaluation before an administrator can approve it.

## Regression design

**IT-SHIP-016** describes the complete four-issue screenshot, list/detail/edit/history boundaries, later Delivered/POD advice, retained identity and quantity controls, matching and legacy overrides, direct delivery with missing or subsequently removed POD, stale bindings, escaped/no-JavaScript rendering, payment coexistence, and unchanged approvals/history/events. It also covers rejected dispatch edits, subsequent evidence refresh, unavailable represented shipments and partial-shipment isolation. Native MySQL cases cover current reads of reservation status, packing lines, documents, gate-step state and revoked overrides after an older snapshot; they do not prove deadlock freedom. Existing IT-SHIP-014/015 cases are adjusted only where this decision intentionally changes the expected result. Approval changes alone do not automatically refresh the current dispatch snapshot; use **Run gate checks** or review it during the next status change. A warning is a point-in-time observation, not a reservation of approvals, documents, packing, QC, or payment.

The initial regression designs were written before production changes but were not run Red. The user subsequently requested the repository's verification before committing. The results below are retrospective, not a test-first Red/Green claim; all databases, credentials and storage were disposable.

An initial fixture failure was corrected to use the non-redirecting dashboards route before this run.
- Full portable Unit, Integration and Feature suite with the same runner and environment, `.work/tools/php/allphp vendor/bin/phpunit -c phpunit.xml --display-errors --display-warnings`: **897 tests, 22,899 assertions passed** in 5m14s. - After fresh migration on a socket-only disposable MySQL 8.0.14 database, the same runner with `APP_ENV=testing`, `DB_CONNECTION=mysql`, `DB_DATABASE=misspack_erp_test`, its disposable `DB_SOCKET`, and `TEST_PHP_BINARY`, `vendor/bin/phpunit -c phpunit.mysql.xml`: **68 tests, 716 assertions passed** in 30s. The five new snapshot cases show specific current reads, not exhaustive concurrency or deadlock freedom.

The existing payment-warning and list-status Chromium checks also passed. These were emulated viewports, not physical-device checks.
- `npm run test:contracts`, the project-workflow and status source checks, PHP/Node syntax and `git diff --check` passed; route inventory reported **514 routes**. Catalogue generation validates references, not coverage. No production deployment is claimed.

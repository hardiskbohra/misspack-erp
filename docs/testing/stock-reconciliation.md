# Stock reconciliation and manual ledger

## Scope and decisions (2026-11-04)

The user chose a **manual ledger**, **product + variant + batch/lot** identity with expiry where applicable, **one stock location**, and an **independent approver** for physical counts. They initially asked not to run test cases unless requested, then explicitly chose to run verification before updating the PR. The existing product `ready_stock_available` field is a sales/catalogue flag, not a balance; invoices, converted purchase documents, packing lists and shipments do not post stock movements. No historical quantities are inferred or backfilled from those records. This first release tracks company stock quantities, not accounting valuation, reservations, conversion between units, multiple locations, transfers, automatic document postings, consignment or public/portal stock.

Catalogue: UT-STOCK-001 and IT-STOCK-001–005. Linked designs and source inventory are not runtime coverage counts. The results below apply to the prior manual-ledger release at `5386b50`; subsequent edit/archive results are recorded separately in [stock-register-edit-delete.md](stock-register-edit-delete.md).

## Acceptance criteria

1. Office users with `operations.view` can view the stock register, batch details and count history; only `operations.manage` can create or change records. Employee, client/vendor portal and unauthenticated users cannot access office stock routes.
2. A stock item combines an existing product, descriptive variant and optional batch/lot; an optional expiry is tied to a named batch. The unit is explicit; later corrections do not convert quantities. Normalized product/variant/batch identity is unique, including archived identities; don't conflate different variants, lots or units, add quantities across incompatible units, or assume the product's old ready-stock flag is a quantity.
3. Creating an item requires an explicit, nonnegative opening quantity, including an intentional zero. Every item has an immutable opening movement. Manual receipts and issues require a positive quantity and reason; reference text is optional. Quantities use exact three-decimal fixed-point arithmetic; no negative on-hand or overflow is allowed. Ledger movements are append-only and show actor, time, quantity, reason, reference and running balance. Before new movements or snapshots, the cached balance/revision must match the latest ledger row; disagreement blocks the action for administrator investigation rather than silently repairing it. This check is not a full historical ledger audit. An accidental entry must be corrected with a later movement or an approved count, never edited/deleted.
4. A physical count is an explicit selection of up to 100 stock items, including zero balances if selected. Creation records each item's book quantity and ledger revision. The creator is the sole counter for that count; blank is **not** zero. Each selected item must have a nonnegative count before submission; each nonzero variance needs a reason. Drafts can be saved partially. Count, product, variant, batch, expiry and unit snapshots remain visible in the review/audit history.
5. A different authenticated `operations.manage` user must approve/post a submitted count and give a reason. The counter cannot approve or reject their own submission. Posting all adjustments and marking the count posted is atomic and idempotent; zero variances create no artificial stock movement. Decisions are immutable history. The reviewer may reject with a reason, returning the count to the counter for correction; a count can also be cancelled with a reason.
6. Real movements are allowed during a count, but **any** change to a selected item's ledger revision after its snapshot makes the count stale, even if the net balance returns to the old value. Posting must fail without changing anything. The counter can explicitly refresh a draft's book snapshots, which clears entered counts and requires a recount; submitted counts must first be rejected. Snapshot, counter, decisions and prior submitted values remain auditable. Each count action also submits the count revision shown to its user: stale draft/review forms cannot overwrite a newer draft or approve a later submission they have not reviewed.
7. Lock item rows in a stable order for count creation/refresh/post and for manual movements, and lock the count before its lines. Duplicate requests or concurrent movements/approvals must not duplicate posts, lose updates, bypass independence or make stock negative. Protect products with stock history from deletion; do not delete media before the database deletion succeeds. A migration rollback must refuse populated stock data; use a consistent backup, maintenance window and stopped writers for MySQL DDL.
8. Register and detail screens use shared master list/forms/components, theme tokens, clear empty/error states, descriptive accessible labels and mobile layouts. Expired or soon-expiring stock is flagged but not silently blocked. No product, invoice, shipment, public tracking or portal semantics are changed by this manual module.

The combined focused stock and shipment run then passed **27 tests / 424 assertions**.
- The JSON float regression initially reached a redirect rather than the expected validation response. A retrospective Red with the stock-specific JSON exception handling removed failed **1 test / 2 assertions** (HTTP 302 instead of 422); restoring it makes JSON stock validation return 422 without posting. Ordinary web forms keep their existing redirect behavior.

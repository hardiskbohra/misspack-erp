# Shipment status from the listing

## Acceptance criteria

1. An office user with `operations.manage` can open an **Update status** dialog directly from each shipment's row. It identifies the selected shipment and its current status; users with `operations.view` can see the status but not the write action. The link falls back to the existing tracking tab without JavaScript.
2. The dialog uses the existing shipment-history route, status options and permissions. It records the chosen status, location, time, remarks, optional delivery date, public-tracking choice and client-notification choice. Unchecking either checkbox must submit `0`, not silently use the existing endpoint's `true` default. Existing tracking history, event dispatch, client notification and project-readiness behaviour stay authoritative.
3. Hold/delay explanations, date ordering, delivery defaults and project dispatch/packing/QC/document gates remain enforced on the server. Leaving a delivery date blank retains an existing date or records the normal business-day default for a first delivery.
4. Return to the same filtered/paginated shipment list. On validation or a stale displayed status, reopen the same shipment's dialog with its unsaved fields and clear errors, even if the row is no longer on the visible page. Do not allow a hidden shipment ID to retarget the action. A status changed since opening is rejected under the shipment lock; the refreshed dialog shows the current value before retry. This status comparison is not a general record revision and cannot detect a status changed away and back to the same value.
5. Follow shared modal, field, button and responsive patterns. Label controls and dialog, support keyboard dismissal/focus recovery, keep status and action accessible on phones, and render user-supplied names and validation errors as text.

## Regression design

- **IT-SHIP-014**: `tests/Integration/ShipmentListStatusTest.php` covers action visibility, permissions, the filtered-list redirect, correct history/event/visibility/notification effects, delivery dates, hold validation, malformed and stale recovery, safe targeting, legacy detail-form compatibility, and project dispatch gates.
- `tests/Database/MySqlShipmentListStatusTest.php` and its guarded worker design one ordered race: the list update observes a newer status after waiting for a shipment row lock. This is not an exhaustive concurrency proof.
- `tools/checks/shipment-list-status-browser.cjs` and its guarded fictional fixture describe interactive row targeting, desktop/mobile layout, validation recovery, stale status, public visibility, keyboard use and read-only access. Browser checks require disposable SQLite/storage under `.work` and loopback only.

## Verification performed (2026-11-05)

The user explicitly requested testing for this submission. The initial acceptance criteria and regression designs were written before implementation, but were **not run Red** before production changes. These results are retrospective verification, not a claim of feature-wide test-first Red/Green.

All PHP tests used fictional data. The environment supplied a PHP 8.4.26 Cecil micro runner and a disposable, socket-only MySQL 8.0.14 instance; the browser used PHP 8.4.21, a separate SQLite database and storage under `.work`, and Chromium 153. The micro runner needs `APP_RUNNING_IN_CONSOLE=true` to match Laravel's normal CLI test detection, and `TEST_PHP_BINARY` for child workers; application CSRF handling was not changed.

- `APP_RUNNING_IN_CONSOLE=true TEST_PHP_BINARY="$PWD/.work/tools/php/allphp" .work/tools/php/allphp vendor/bin/phpunit -c phpunit.xml --filter 'ShipmentListStatusTest|ShipmentDetailTabsCommentsTest'`: **28 tests, 423 assertions passed**.
- With the same environment, `.work/tools/php/allphp vendor/bin/phpunit -c phpunit.xml`: **855 tests, 22,381 assertions passed** in 3m27s. One existing PHPUnit notice concerns a mock transport without expectations in `SalesInvoiceEmailTest::test_a_refused_send_is_logged_and_briefs_the_desk`.
- Fresh `artisan migrate --force` on the guarded disposable `misspack_erp_test` database, followed by `.work/tools/php/allphp vendor/bin/phpunit -c phpunit.mysql.xml` with `APP_ENV=testing`, `APP_RUNNING_IN_CONSOLE=true`, `DB_CONNECTION=mysql`, `DB_DATABASE=misspack_erp_test`, the disposable `DB_SOCKET`, and `TEST_PHP_BINARY`: **62 tests, 691 assertions passed** in 21s. The new focused MySQL race passed **1 test, 7 assertions**. The test proves one ordered stale-status interleaving, not every concurrent writer or status ABA.
- With the fictional fixture seeded into the guarded SQLite database and `SHIPMENT_LIST_BROWSER_BASE_URL`, `SHIPMENT_LIST_BROWSER_PASSWORD`, `CHROMIUM_EXECUTABLE_PATH`, and the isolated Chromium library path set, `node tools/checks/shipment-list-status-browser.cjs` passed at **1440, 768, 390 and 320 px**. It exercised targeting, modal focus and dismissal, filter-preserving validation and delivery, private tracking, stale recovery, read-only permissions, and the actual JavaScript-disabled fallback.
- `npm run test:contracts` passed; `php tools/testing/export-routes.php --check` inventoried **514 routes**. Design, status, SQL, project-workflow, workflow UX, packaging, UI-component and confirmation checks passed **79/79, 20/20, 5/5, 115/115, 17/17, 117/117, 24/24 and 53/53** respectively; the confirmation check included Chromium.
- PHP/Node syntax checks passed. `artisan view:cache` and linting all **293 compiled Blade templates** passed, followed by `artisan view:clear`.

During setup, the first shipment run hit CSRF failures because the micro SAPI was not recognized as console; setting the test-only environment above fixed the runtime. Two in-process session assertions were changed to verify the actual redirected page instead, avoiding double-marshalling Laravel's JSON error bag; an unrelated office briefing can include a filtered-out shipment number, so targeting is checked against the specific modal and action. The browser harness was corrected for CSS-uppercase status text and Playwright's `javaScriptEnabled` option. The micro runner's argument count was corrected before the MySQL race rerun. A source check's fixed character window was replaced with a method-scoped check of the same delivery-default call.

The optional `node tools/checks/list-check.cjs` reported **117 passed and 4 failed**; the exact same four failures were reproduced against clean baseline `fec1728` (existing cashflow/list-chrome, chip-wrapper and period-count checks). They were not changed or presented as passing here. No physical device, live warehouse, production database, external delivery, or exhaustive concurrency schedule was tested.

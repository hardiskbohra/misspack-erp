# Vendor statement project names

## Acceptance (REQ-STATEMENT, IT-STATEMENT-009)

- In a vendor statement's **Particulars** cell, show the linked project name(s) prominently, labelled `Project:` or `Projects:`, while retaining the existing description, date, reference, debit (paid), credit (billed), status and running balance. Show the same data in the office view, print/PDF fallback and guest vendor statement share.
- Use project links actually recorded on the vendor ledger row, its purchase document, its purchase-payment splits, its linked cashflow or that cashflow's project/purchase-document allocations. A payment split across projects can name each linked project without splitting or duplicating the monetary row. Include soft-deleted/archived project names for historical statements. A missing, blank or unlinked project leaves the old particulars intact; do not infer a project from free text or the vendor's other jobs.
- Never derive a name from a purchase document or cashflow explicitly owned by another vendor; ignore allocation links to another vendor's purchase or to a sales document. A legacy cashflow matched only by name may supply its project only when its vendor name matches exactly, not merely as a substring. An explicitly recorded project on the vendor's own ledger row remains authoritative.
- Preserve converted-PO visibility, currency/date filters, figures and transaction order. Names are plain escaped text. Client statements do not gain this vendor-only detail. Fetch project details in batches rather than one query per statement row. Missing optional project/allocation schema must not break a legacy statement.
- Resolving names makes no ledger/project writes, financial recalculation, schema migration or external delivery. Existing public-share view tracking remains unchanged.

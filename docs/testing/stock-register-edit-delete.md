# Stock register editing and removal

## Decision and acceptance criteria (2026-11-04)

The user requested edit/delete on the stock register and selected **item details plus quantity** and **archive with retained history**. Quantity changes are requested by the editor but require a different operations manager to approve before any balance changes. Existing receipts, issues and count decisions remain immutable. Deleting means archiving, not destroying data; restoration must be available.

1. Operations managers can correct a stock item's product, variant, batch, optional expiry and unit, with a reason. Identity normalization and uniqueness continue to apply, including archived items. Editing corrects an existing identity; it is not a transfer, unit conversion or creation of a separate batch. Previously recorded count snapshots and movement identity/unit must remain understandable, with before/after audit history and actor. An edit must not automatically rewrite quantities.
2. The edit form displays the current balance and accepts an exact requested balance. If different, create and submit a one-item physical count with the stated reason, without posting stock. A different operations manager must approve or return it using the existing count workflow; the counter cannot approve their own request. Stale item or ledger revisions cannot overwrite newer edits or generate duplicate correction requests. Validate the requested quantity as a decimal string; reject negative, over-precision and JSON float inputs.
3. An item identity change invalidates any open physical count snapshot of that item even if quantity did not change. A stale submitted count must be returned, refreshed and recounted before approval; prior snapshots and decisions remain in its history.
4. Delete archives an item, records a reason and actor, retains its full ledger and counts, and offers restoration. Archived identities remain reserved to avoid duplicate ledgers. Archived items do not accept new movements or new counts. Block archiving while a count involving the item is open. An item with a nonzero balance can be archived only after a clear warning and explicit acknowledgement; its balance remains visible in the archive and an active-register warning, never silently discarded. Restore must retain the same balance and history.
5. Only `operations.manage` may edit, archive or restore; `operations.view` can inspect active/archived records and histories. Server-side validation and transactions must protect forged requests, stale forms, duplicate identities, missing products and concurrent count/movement/archive operations. Keep product deletion protection for all stock history, including archives.
6. Use shared cards, inputs, buttons, responsive tables and confirmation dialogs. Provide labelled edit and delete actions from the register/detail, clear archived status, accessible reason and acknowledgement fields, informative validation and a safe recovery path for stale unsaved edits.
7. A manual movement form opened before an item correction or archive/restore decision must not post against a different identity. Require the displayed record revision for new movement submissions, check it under the item lock, preserve unsaved input separately, and continue treating an exact retry of a previously posted request as idempotent. Forms/clients from before this change must reload before posting.

## Implementation and regression inventory

- Catalogue designs **IT-STOCK-006–009** link the new integration and native MySQL methods. These links describe intended evidence, not runtime results or coverage.
- `tests/Integration/StockRegistryEditArchiveTest.php` describes details/history, original-product protection, migration backfill, exact quantity requests, independent approval, stale count/edit/movement/archive recovery, duplicate archived identity, access and rollback refusal. The migration upgrade case uses only isolated in-memory SQLite.
- `tests/Database/MySqlStockRegistryTest.php` covers a populated native upgrade and product-history backfill, historical-product foreign-key protection, and two ordered archive races: a receipt that changes the ledger, and creation of an open count without changing the balance. The upgrade case creates and removes randomly prefixed fixture tables on a separate connection; the tests and worker refuse a non-testing or non-`*_test` database. Earlier native stock fixtures were updated to clean up the new history references.
- `tools/checks/stock-reconciliation-browser.cjs` has additional scenarios for desktop/mobile edit, stale input recovery, approval, open-count archive blocking, nonzero acknowledgement and restore. Its guarded loopback-only fixture is fictional and disposable.
- New movements snapshot identity at posting. Existing movements are labelled with the identity available before the first correction; prior changes to product names or identities that were not recorded cannot be reconstructed. The migration backfills only product references for the existing immutable item identities, not historical document quantities. The product-history foreign key keeps even a formerly assigned product from deletion.
- Edit and decision forms use record and ledger revisions; manual movements require the record revision. An identity change stales open counts; archiving is blocked while any open count exists. The item lock serializes competing count creation, movements and registry decisions. On MySQL, a count decision locks its header before item rows while archive checks open count rows after locking the item: a deadlock is possible under competing operations and transactions retry up to three times. The selected native cases do not establish correctness for every concurrency interleaving.
- Apply migrations with a consistent backup and stopped stock/product writers. MySQL DDL auto-commits and partial failures require deliberate recovery. Both stock migrations guard against discarding protected history on normal rollback.

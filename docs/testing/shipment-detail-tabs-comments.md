# Shipment detail tabs and internal comments

Catalogue: IT-SHIP-011 (record tabs), IT-SHIP-012 (internal comments/private attachments), and IT-SHIP-013 (schema/rollback and locking).

## Acceptance criteria (2026-11-02)

- Reorganize the existing shipment detail into URL-addressable Overview, Tracking, Products & delivery, Costs, Documents and Comments tabs using the same shared record-tab visual treatment as the vendor detail. The persistent header identifies the shipment and status, and keeps the primary navigation/actions available. Each URL renders only its own panel, can be bookmarked/opened directly, works with browser back/forward, has an accessible active state, and falls back safely for an unknown tab. Do not remove existing information, forms, print/packaging/tracking links or operational protections.
- Keep route details and tracking progress in Overview; tracking share, update and history in Tracking; items, packaging-list actions and receipt reconciliation in Products & delivery; cost breakdown/actions in Costs; print actions and existing shipment uploads in Documents. Follow existing theme tokens and responsive layout, avoiding page-level horizontal overflow on phones.
- Existing links that request `record_delivery_receipt=1` must open the delivery form in the Products & delivery panel. Successful receipt/upload/comment actions must return to the corresponding tab; validation must leave the operator on the relevant form with readable errors and preserved text. Existing shipment attachment fragment links remain useful.
- Allow an operations manager to add a text comment with zero to five optional files, each at most 10 MB. Explicitly list supported file types in the UI; reject invalid, oversized, mixed invalid and forged uploads without persisting any comment or files. Long comments and filenames wrap; render user-supplied content as text. Show author, date/time and each file on its own comment, newest first. Empty state is clear. Comment attachment files are private and unrelated to the shipment's public/document checklist.
- User chose **internal team only**: neither comments nor their attachments appear on public tracking, client portal, printouts or public media. Store files on the local/private disk; serve only through an authenticated office route requiring `operations.view`, verify the shipment/comment/file ownership chain, force downloads with no-sniff and no-store headers, and refuse missing files. `operations.manage` is required to add or delete a comment; an operations reader can view/download but not write. An unrelated office user, guest, employee or client portal user cannot access these office routes. Do not use a public disk URL or signed public link for comment files.
- Deleting a comment removes only its own database rows and files; deleting an eligible shipment removes its internal comment files too. Failed database/file writes roll back the comment and remove already-stored files. Preserve existing shipment deletion restrictions, existing client-portal comments and shipment attachment visibility.
- Verification uses fictional records, fake disks and disposable databases. Test HTTP access, validation, ownership, persistence, rollback and cleanup, escaped text, legacy receipt/attachment links, tab selection and all existing actions. Include a native MySQL migration/foreign-key test and interactive Chromium desktop/mobile tab and comment workflows. Update catalogue/routes and record actual commands, Red, Green, full-suite results and limitations before submission.

## Implementation and operations

- Comments are separate from both the existing shipment document checklist and client-portal comments. Only authenticated office users with `operations.view` may view/download; `operations.manage` is needed to add or delete. Downloads verify the shipment → comment → attachment chain and use private, no-store, nosniff, forced-download responses. Files are stored on the `local` disk under `shipments/comments/{shipment_id}`, not the public disk. No comment/file contents are copied into tracking, portal, print views or audit payloads.
- A comment requires text (maximum 4,000 characters) and allows up to five matching PDF, JPG/JPEG, PNG, WEBP, GIF, DOC/DOCX, XLS/XLSX, CSV or TXT files, at most 10 MiB each. These checks and forced downloads are **not malware scanning**. If deletion cannot remove a file, the office user gets a warning and application logs include the relative random paths for administrator cleanup, not comment text or original filenames.
- Before deploying, back up the database **and** private storage, stop writers, run the normal migrations, and bring up the application with `storage/app/private` outside the public document root. All application nodes must use the same protected storage/backup strategy. Match infrastructure limits to the form: `upload_max_filesize` at least 10M, `post_max_size` and proxy/web-server body limits at least 64M, and `max_file_uploads` at least 5. Lower server limits will prevent accepted-in-app uploads from reaching Laravel.
- A normal rollback refuses to drop populated comment tables, avoiding silent loss of discussions and orphaned private files. An intentional removal requires a coordinated, verified database/private-storage backup and explicit removal or migration of data and files before rolling back. MySQL DDL auto-commits; do not rely on a transaction to undo schema changes or allow writers during the check/drop window. If restoring, restore database and private storage together. `migrate:fresh` is destructive and was used **only** on disposable test databases.

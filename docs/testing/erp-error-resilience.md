# ERP error resilience: acceptance and regression plan

## Why the shipment 500 escaped testing

The dispatch gate assembled several legitimate business blockers into one summary, then wrote that prose to MySQL `project_gate_evaluations.summary`, originally `VARCHAR(255)`. Strict MySQL rejected a summary longer than 255 characters with error 1406 instead of returning the expected actionable dispatch rejection. SQLite does not enforce the declared `VARCHAR` length; several existing feature fixtures also built only selected tables. The prior MySQL CI job ran the full migration chain and targeted native tests, but did not execute this real shipment HTTP journey. A green suite describes the scenarios actually exercised, not every operation in the ERP.

On a disposable MySQL 8.0.14 schema, temporarily restoring the old summary type made both the dispatch and ordinary planning-save HTTP regression tests fail with the same `SQLSTATE[22001]`/1406. Restoring `TEXT` made both pass. The dispatch test covers both edit and tracking-history paths with multiple simultaneous blockers; it does not independently prove every prerequisite combination or concurrent dispatch.

## Acceptance contracts and changes

- **IT-SHIP-003 (partial), IT-PROJECT-004:** widen the generated gate summary without losing existing values. Dispatch remains blocked with actionable information and unchanged shipment/history; an ordinary planning save with a long readiness evaluation succeeds.
- **IT-SHIP-009:** reject malformed or null line collections, incomplete meaningful rows, excess decimal precision and values outside storage limits before writing. Accept valid boundary values and empty template rows, including the form's default INR row under a USD shipment. An omitted collection preserves existing lines and dispatch evaluates those stored lines; the editable form's explicit marker permits intentionally clearing every row.
- **IT-BRIEF-009:** generated office-alert, project-exception and client-portal titles and links preserve composed values longer than an individual input's `VARCHAR(255)`. The added migration widens those fields to `TEXT`.
- **IT-SALES-031:** normalised invoice To/CC lists can exceed the 500-character input after formatting. Persist an unconfirmed audit record **before** invoking mail; if the initial write fails, do not send. If recording the outcome fails after invocation, retain an unconfirmed attempt, return an error, and advise checking delivery before retrying. Cap transport error text before inserting it into the audit, alert and response. A transport exception does not prove remote delivery did not occur. One invocation per successful request is tested, not idempotency across repeat requests.
- **IT-WORKFLOW-006 (partial):** fresh SQLite can apply the complete migration chain; the legacy progress copy preserves matched and unmatched project values. Both widening migrations preserve old values and refuse lossy rollback on SQLite and MySQL before narrowing any of their checked columns. Tests create uniquely named disposable MySQL schemas; their account requires CREATE/DROP DATABASE privileges.
- **IT-UI-009:** unexpected HTTP 500s remain failures, suppress exception details, and provide a reference and a warning to check records and external effects before retrying. API/JSON callers receive JSON, including explicit 500 responses. References are correlated with normal exception reports when logging works. Validation, authentication and other tested 4xx behaviour remain unchanged; local debug output remains available.

## Verification and operating limits

The exact commands and latest local results are in [execution-baseline.md](execution-baseline.md). Full-schema HTTP scenarios run against strict MySQL and SQLite with fake storage and fake/in-process mail. SQLite is not evidence of MySQL column enforcement. The fresh MySQL migration command is separate from the isolated upgrade tests. `TEXT` is still finite (up to 65,535 bytes in MySQL), and not every generated field or workflow in the ERP has been exhaustively audited. Native concurrent dispatch, production-shaped database upgrades and real external providers remain independent verification work.

The fallback does not cover web-server/proxy failures, application bootstrap failures, queue jobs or errors after a streamed response has started. A reference cannot be correlated to a log entry if logging itself fails. Use `APP_DEBUG=false` outside development and monitor logging and background jobs independently. A 500 may occur after a database commit or external side effect; it does **not** prove that an email, payment or write did not happen. Some shipment/packaging readiness refreshes and KYC notification work happen after their primary write; this change does not make those operations atomic. Inspect the underlying record and provider before retrying, especially for unconfirmed email attempts.

## Deployment and rollback

After the reviewed commit is deployed from the intended release branch, take a database backup and run `php artisan migrate --force` in the production release. The shipment-summary widening and the new generated-message/recipient widening must both be applied; deploying code alone does not repair the database. Confirm migrations and the shipment journey afterward. No production migration was run by these tests.

Rollback prechecks refuse to narrow fields containing overlength values rather than silently truncating them. Because MySQL DDL implicitly commits and the checks are not atomic with concurrent writes, stop writers before any rollback and use a backup/maintenance plan. Resolve long values deliberately before narrowing; do not assume an interrupted multi-table DDL operation is automatically rolled back.

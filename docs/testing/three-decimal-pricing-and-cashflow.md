# Three-decimal unit prices and cashflow

## User decisions and acceptance

- In proforma invoices (PI), sales invoices, purchase orders (PO) and bills, **unit price** accepts up to three decimal places. Quantities already accept three. Other manually entered invoice fields keep their existing input precision except where an automatically calculated three-decimal round-off must be editable.
- PI, cash-invoice, PO and bill calculated line amounts, totals and outstanding balances retain three decimal places. A rate of `0.574` and quantity `5000` produces `2870`; a quantity of `1` produces `0.574`. Apply discounts, taxes and rounding at three decimals; the live browser preview, server, persisted records, print/detail and amount in words must agree.
- Tax-invoice monetary line, tax and invoice totals stay at **two decimal places**, while their unit price is stored and exported at three decimals. This is the user's explicit GST e-invoice compatibility choice. The existing optional automatic whole-INR rounding stays in force for eligible new proformas and tax invoices; a proforma's automatic adjustment may itself require three decimals. Cash and non-INR invoices are not automatically rounded.
- Conversion must preserve the exact agreed claim and transferred receipts. Do **not** silently round an existing three-decimal PI claim to two decimals while converting to a tax invoice. After an explicit user decision, also refuse partial cash-to-tax conversions whose allocated line gross cannot be expressed by the original item quantity and any three-decimal rate. Reject either case with an actionable message; the PI, existing cash invoices, claims and receipts remain unchanged. Staff may reverse/review the cash conversion or PI terms, rather than issue inconsistent legal figures.
- Cashflow entry amounts, allocations, account running/current balances, and linked invoice balances retain three decimals across create, edit, quick entry, ledger, reports, statements and receipt/payment linking. Invalid fourth-decimal input must be rejected rather than silently rounded. Existing entries and invoices must survive the schema migration unchanged.
- Project product snapshots sourced from a sales invoice retain its three-decimal rate. A save/reload of an issued tax invoice must not conceal a rate change of one thousandth from its existing legal-document lock. No private links or authorization are changed.
- Expand SQL decimal capacity without reducing the pre-existing number of integer digits. Rolling back a schema change must refuse to discard non-zero third-decimal data. Stop writers around schema rollback; MySQL DDL commits independently. The release requires a database backup and `php artisan migrate --force` before writes.

GST IRP references describe three-decimal unit prices and two-decimal assessable/tax/invoice values: https://gsthero.com/blog/e-invoice-format-a-detailed-breakdown-of-e-invoicing-schema/. Portal validation also reconciles line and invoice components: https://einvoice6.gst.gov.in/content/validation-rules-for-e-invoicing-that-you-must-take-care-to-avoid-errors/. No live tax portal will be contacted by the tests.

E-invoice preflight checks the saved rate × quantity, item discount/tax/total, discounted header totals, and the IRP round-off range. The existing invoice-wide discount is allocated to item discounts at paise precision, using the same largest-remainder approach as the printed invoice; it is not deducted a second time at the invoice level. If the saved amounts cannot be allocated consistently (including a tax-rate mismatch), e-registration is refused with a review message rather than exporting altered figures. This is intentionally conservative and does not claim a live IRP accepted the payload.

Relevant designs: **IT-SALES-032–038**, **IT-PURCHASE-004**, **IT-CASH-007–008**, **IT-WORKFLOW-007**, **IT-TAX-012–013**, and **IT-PROJECT-005**; other catalogue cases remain broader. Original cash-conversion success scenarios now use an exactly representable 50% split while retaining their claims, receipt conservation, metadata and GST assertions. Separate new regressions cover the newly user-selected refusal for the former unrepresentable quantity/rate shape. Cumulative gross allocation retains the existing paise behavior for wholly paise inputs, but uses thousandths when the claim, taxable base or cash-conversion slice needs them: a `0.001` cash conversion must consume `0.001`, even when the original PI was exactly `1.00`.

## Implementation and deployment

The migration widens existing DECIMAL fields without reducing integer capacity, preserving nulls/defaults. It covers invoice item rates and relevant totals, cashflow balances/allocations, vendor payments and project snapshots. Existing two-decimal values do not change. A shared adaptive decimal cast keeps legacy two-place model serialization where possible while retaining a significant third digit. Do not recalculate historical invoice claims in a deployment migration.

Before deployment, take and verify a database backup, stop or quiesce writers, deploy the code and run `php artisan migrate --force`; restart writers only after confirming the migration completed. MySQL DDL can commit independently, so a transaction cannot undo a partially completed schema migration. The migration checks table/column existence to make an interrupted upgrade safer to resume; test restoration from the backup if necessary. **Do not roll back while any affected value needs the third decimal:** the downgrade preflights data and refuses a lossy conversion. Quiesce writers throughout the rollback too, because writes between preflight and MySQL DDL could invalidate that check. Restore from the verified backup if a downgrade is needed and values cannot safely fit the old schema. No production database was modified during this work.

## Verification (2026-10-28)

- Red-first integration tests exercised three-place rate/amount persistence and unsafe conversion/e-invoice cases. The originally unrepresentable partial conversion was changed only after the explicit block-conversion decision. An invoice-wide discount payload test also failed before item allocation was implemented; a Chromium check exposed and then verified the cash-conversion transfer cap at `0.574`.
- Complete portable PHPUnit: **682 tests / 17,566 assertions**, with one existing PHPUnit mock-configuration notice. Native strict MySQL: **31 tests / 352 assertions**, including HTTP persistence, conversion atomicity, e-invoice discount allocation and safe/unsafe migration rollback. The suites were run serially; SQLite is not a substitute for MySQL DECIMAL/DDL behavior.
- Chromium: PI, tax, PO and bill create/preview/save/print/edit at 1440 px and 390 px; cashflow save, three-place running balance and rejection of excess allocation; whole-INR rounding at 1440/768/390 px and live save/edit; conversion transfer-cap fixture **31 checks**. No live IRP, physical printer or phone was tested.
- Catalogue/inventory generation, `npm run test:contracts`, invoice and vendor-portal source checks, PHP/JavaScript syntax, route inventory and diff-whitespace checks passed. These inventories are not runtime coverage claims.
